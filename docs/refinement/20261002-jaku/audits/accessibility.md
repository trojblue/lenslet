### Shared menu keyboard follow-up

Source review of `frontend/src/shared/ui/ThemeSettingsMenu.tsx` and `frontend/src/app/menu/ContextMenu.tsx` found declared menu/menuitem semantics without the corresponding focus-entry or Arrow/Home/End behavior. This is a systemic keyboard interaction finding (HIGH under the keyboard-path escalation). Implemented one `useMenuKeyboard` hook for these two existing menu owners; the established Dropdown keyboard model stays separate. It waits for visible, positioned content, focuses one item, uses roving tabindex, supports Arrow/Home/End and short typeahead, lets embedded input/Dropdown handlers win, and returns focus on Escape. ArrowUp on Settings opens at the last item; ordinary opening starts first.

The first browser regression check caught Tab dismissal sending focus to body after a portal unmounted. Fixed the shared owner: calculate the adjacent tabbable relative to the original trigger, wrap only within an owning modal, and focus it during cleanup after preventing native Tab. This retains the expected next-control path without trapping users in the menu.
